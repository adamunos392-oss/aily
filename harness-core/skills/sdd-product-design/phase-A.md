# 阶段 A：产品定义

阶段 A 的目标是把“为什么做、给谁做、解决什么问题、做到什么范围”锁定为明确的产品定义。

## 固定产出

`docs/PRD.md`（阶段 A 完成产品定义，阶段 F 补充 Feature 追踪关系，阶段 C 完成最终定稿）。

## 阶段边界

阶段 A 必须定义：

- 产品目标与成功结果
- 用户角色与职责
- 核心业务场景和端到端旅程
- MVP 范围、V2+ 与明确非目标
- 业务规则、权限原则和关键约束
- 业务数据概念及生命周期语言
- 外部服务候选项和已知风险

阶段 A 禁止提前锁定：

- 数据库表名、字段名、字段类型、索引和迁移方案
- API 路径、请求体、响应 DTO 和错误码明细
- 前后端文件路径、类名、组件名和内部模块结构
- “一个页面等于一个功能”或“一个接口等于一个功能”的拆分结论
- 尚未经过 Feature Map 验证的技术实现方案

允许在 PRD 中出现业务级数据表达，例如“工单具有待处理、处理中、已完成状态”；不得在此阶段出现类似： `tickets.status VARCHAR(32)`的表述。

## 执行顺序

```text
A1 产品目标与用户
→ A2 核心场景与用户旅程
→ A3 范围、业务规则与非目标
→ A4 版本规划、风险与外部依赖
→ A5 PRD 产品定义确认
```

禁止跳过前面的产品问题，直接讨论页面、接口或数据表。

---

## A1：产品目标与用户

先对齐产品存在的理由。

### 必须回答

1. 产品服务哪些用户或角色？
2. 每类用户当前遇到什么具体问题？
3. 当前做法存在哪些不足，用户为什么会选择这个产品？
4. 什么结果能证明 MVP 有价值？

### 输出格式

```markdown
## 产品目标

- 目标用户：
- 当前问题：
- 产品承诺：
- MVP 成功结果：
- 明确不承诺：

## 用户角色

| 角色 ID | 角色 | 目标 | 当前阻碍 | 允许做什么 | 不允许做什么 |
|---|---|---|---|---|---|
| R-001 | 员工 | 快速获得问题答案 | 信息分散 | 发起咨询、查看自己的会话 | 管理知识库 |
```

---

## A2：核心场景与用户旅程

这一阶段定义用户如何从触发点到达业务结果，但不拆 Feature，不设计接口。

### 要求

- 主流程必须覆盖产品核心价值
- 跨角色场景必须写明交接点
- 不得用“调用接口”“写入数据库”等技术动作代替用户动作
- 暂时不按页面组织；页面只能作为可能的交互载体

---

## A3：范围、业务规则与非目标

### MVP 范围

```markdown
## MVP 范围

| 场景 | MVP 必须成立的业务结果 | 深度边界 | 延后内容 |
|---|---|---|---|
| S-001 | 员工可以提交问题并获得处理结果 | 单组织、单语言 | 多组织、多语言 |
```

### 业务规则

业务规则必须使用业务语言，不能依赖具体数据库或 API 设计。

```markdown
## 业务规则

| 规则 ID | 规则 | 适用场景 | 违反时结果 |
|---|---|---|---|
| BR-001 | 已完成工单不能再次接单 | S-002 | 拒绝操作并提示状态已变化 |
```

### 业务数据概念

只定义业务对象的意义和生命周期，不定义物理字段。

```markdown
## 业务数据概念

| 概念 | 业务含义 | 由谁产生 | 生命周期 |
|---|---|---|---|
| 工单 | 一次需要人工处理的问题记录 | 系统或员工 | 待处理 → 处理中 → 已完成 |
```

### 非目标

所有“暂不做”“V2+ 再做”“不支持”的内容必须显式列出，防止 Feature 拆分和验收标准擅自扩张。


---

## A4：版本规划、风险与外部依赖

阶段 A 的版本规划按用户结果和场景划分，不按页面或技术模块划分。

```markdown
## 版本规划

### MVP

| 场景 | 必须达到的结果 | 纳入理由 |
|---|---|---|
| S-001 | 员工可以完成一次咨询闭环 | 产品核心价值 |

### V2+

| 结果 | 延后理由 | 前置依赖 |
|---|---|---|
| 多语言咨询 | 非 MVP 核心 | 多语言模型与内容体系 |
```

### 外部依赖候选清单

此处只记录业务依赖和未知项，不索取真实密钥，不确定具体 SDK 封装。

| 服务类别 | 业务用途 | MVP 必需 | 未确认事项 | 缺失时业务影响 |
|---|---|---|---|---|
| LLM | 生成回答 | 是/否 | 供应商、模型、额度 | 只能进入人工流程或 Mock/fallback |

### 风险

- 业务规则尚不确定的风险
- 外部服务可用性风险
- 权限和隐私风险
- 跨角色流程无法闭环的风险

**门禁**：用户确认版本规划、外部依赖和风险后，才能进入 A5。

---

## A5：PRD 产品定义确认

### PRD.md 建议结构

1. 背景与调研结论
2. 产品目标与成功结果
3. 用户角色与权限原则
4. 核心业务场景与用户旅程
5. MVP 范围、V2+ 与非目标
6. 业务规则
7. 业务数据概念与生命周期语言
8. 外部依赖候选清单
9. 风险与约束
10. 产品定义确认记录

### 产品定义确认记录

PRD 末尾必须写入以下章节，供 Skill 路由判断阶段：

```markdown
## 产品定义确认记录

- 状态：已确认
- 确认范围：产品目标、用户角色、核心场景、MVP、业务规则、非目标
- 尚未锁定：Feature 边界、物理数据模型、API 契约、实施方案
- 下一阶段：F（Feature 架构与功能规格）
```

### 自检

- [ ] 每个 MVP 场景都有明确角色、触发条件和业务结果
- [ ] 业务规则使用业务语言表达
- [ ] 非目标和 V2+ 已明确
- [ ] PRD 没有锁死数据库字段和 API DTO
- [ ] PRD 没有把页面、接口或表直接当成 Feature
- [ ] 没有 `TBD`、含糊的“后续再定”或相互冲突的约束

自检不通过时继续在阶段 A 修正，不得进入 Feature 拆分。

## 阶段 A 总确认

向用户展示：

- 产品目标与用户摘要
- 核心场景清单
- MVP / V2+ / 非目标
- 关键业务规则与风险
- 明确尚未锁定的技术内容

发起门禁问题：

> 产品定义已经完成。是否确认进入阶段 F，开始拆分 Feature、梳理功能依赖和业务数据关系？

未经用户确认，不得进入阶段 F。
