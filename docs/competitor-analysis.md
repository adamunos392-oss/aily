# 竞品分析：Aily 企业智能助手

调研日期：2026-09-21  
产品方向：企业内部智能办公助手 Demo（求职演示）。员工用自然语言完成知识问答、内容生成、实时查询、任务执行；工作台右侧用 **Agent 事件流** 展示本次真实执行过程。  
明确不做：生产级 Aily、飞书嵌入、Planner / ReAct / Multi-Agent、开放式自主规划。

本文件只服务阶段 R。已确认的 Demo 边界见文末「阶段 R 输入」，不在此锁 PRD。

---

## 竞品一：飞书 Aily（智能伙伴平台）

- 一句话定位：给企业搭建者配置、给员工在飞书/对话应用里使用的企业智能伙伴；用知识、技能和工作流回答问题并办事。

**① 做了哪些功能**

- 四种对话模式：模型推理（Agent 选工具）、工作流、知识问答、混合调度。
- 知识接入：本地文件、飞书云文档、业务系统、数据库；支持标准问答对拦截。
- 问答规则：生成指令、召回数量与匹配阈值、多轮意图改写、是否展示参考来源、拒答话术。
- Workflow 技能：固定节点编排（LLM、字段提取、知识问答、条件分支、HTTP、调用其他技能等）；混合调度下也可被模型选中。
- 运行日志：按对话查看用户输入、命中技能、执行状态、耗时、Token；详情里逐节点看输入输出。面向搭建者/运维，不是员工聊天右栏。
- 调优台 / 用例：把一次问答拆成检索、切片、生成等步骤，人工纠偏后沉淀用例。
- 员工入口：对话应用、飞书机器人、Web SDK。

**② 功能取舍的逻辑**

- 做深知识问答与调优，因为企业落地的核心是「答不准、不敢用、无法干预」；无知识时用拒答话术，避免编造制度。
- 做深飞书套件连接，因为目标用户已在飞书办公。
- 提供 Agent / Workflow / 混合调度，是为了从「问答」升级到「办事」；对只要验证产品逻辑的团队过重。
- 运行可视化放在日志和调优台，因为真实产品要把「过程」留给管理员，员工侧保持聊天简洁。
- 明显缺失（相对本 Demo）：员工对话主界面没有常驻的、按 turn 追加的 Agent 事件流；WRITE 确认、timeout→UNKNOWN、确认单失效不是员工侧一等公民。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：搭建后台是左导航 + 中间编排/知识 + 右侧重试/日志；员工侧以对话流为主，引用可在回答下展示。过程详情进「运行日志 / 调优」二级页。
- 视觉风格：飞书蓝白、企业 SaaS、信息密度高、少营销风。
- 配置方案：模式、模型、知识、问答规则、技能编排、开场白均给搭建者；员工几乎只聊天。

## 竞品二：钉钉 AI 助理

- 一句话定位：给组织内员工用的办公助理；把知识问答、自定义技能、工作流和安全策略配在一个助理上，在钉钉会话里完成查询和办事。

**① 做了哪些功能**

- 技能组合：自定义能力（OpenAPI/脚本接业务）、工作流、拟人操作、知识问答、规划、安全敏感词。
- 知识：钉钉文档/知识库、网页、本地文件、FAQ；有「学习中 / 失败」状态。
- 互动：对话框上方快捷按钮（链接、锁定技能、预设提示词）。
- 调试：预览页看技能调用节点的请求/响应、耗时；面向开发者排错。
- 高风险操作确认（平台/CLI 侧已出现门禁思路）：先展示摘要，用户明确确认后再执行。

**② 功能取舍的逻辑**

- 做深「助理 = 技能包」，方便企业把已有 OpenAPI 变成员工可说的能力，而不先做完整 Agent 平台。
- 规划技能服务开放式目标拆解；与本 Demo「禁止 Planner」相反，不能搬。
- 调试日志给开发者，不给普通员工解释 Agent 链路。
- 明显缺失：员工侧三栏工作台 + 与消息同步的事件流；Citation 深度、评测/Bad Case 页不是产品一等公民。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：创建页分区配技能/知识/安全；使用侧嵌在钉钉会话，上方快捷操作，中间对话。
- 视觉风格：钉钉蓝、会话气泡、偏 IM 而非独立宽屏工作台。
- 配置方案：创建者配技能与可见范围；组织管理员管范围；员工不配 Pipeline。

## 竞品三：Dify 对话应用（辅以 LangGraph/LangSmith 的可解释对照）

- 一句话定位：给搭建者快速做出可发布的知识对话/Agent Web 应用；员工看到的是左会话 + 中聊天，过程日志主要在工作室调试态。

**① 做了哪些功能**

- 聊天助手：关联知识库，开启「引用和归属」后在回答下方展示文档/分段来源。
- WebApp：新建/置顶/删除会话，来源引用，偏 ChatGPT 双栏。
- Agent 节点：可走 Function Calling 或 ReAct；输出含 Tool Outputs、Reasoning Trace、Agent Logs（JSON/调试态）。
- LangGraph 一类框架（非 Dify 本体）：把 WRITE 做成 interrupt → 人确认 → resume；LangSmith 用 **run/event 时间线** 而不是一张固定流程图看一次调用。

**② 功能取舍的逻辑**

- 做深「能发布的对话应用」和引用开关，降低做 RAG Demo 的成本。
- Agent/ReAct 给开放任务；本 Demo 明确禁止，只借鉴其「过程是事件、不是静态图」。
- 确认门禁在框架层很完整，但默认 UI 不是企业员工工作台，也很少把 Risk/Permission、Confirmation、Result Validation 做成员工可读的中文事件。
- 明显缺失：企业制度拒答纪律、同名人员消歧、确认单随 Slot 失效、评测 Case 页与员工工作台同屏演示。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：左会话列表，中消息流 + 输入框；引用挂在回答底部。Trace/日志在搭建者调试面板或独立可观测产品里。
- 视觉风格：中性白底、产品工具风；可做成企业风，默认不是飞书工作台。
- 配置方案：模型、知识、召回、引用开关、工具列表给搭建者。

## 方案对比与推荐

| 方案 | 来源 | 本 Demo 该学 | 不该整套搬 |
|------|------|-------------|------------|
| A | 飞书 Aily | 有据才答、Citation、拒答、Skill 固定编排、过程可追溯的产品意图、企业蓝白工作台风 | 四种模式、混合调度、开放模型推理、调优台、飞书套件、把 Trace 藏进管理员日志 |
| B | 钉钉 AI 助理 | 技能=办事能力、快捷入口、WRITE 先确认、员工是使用者不是开发者 | 规划技能、钉钉会话嵌套、拟人操作、组织可见范围体系 |
| C | Dify（+ HITL/事件追踪对照） | 左会话+中对话、引用与归属、过程按 **事件/run** 追加、WRITE interrupt 再 resume | ReAct 循环、搭建者调试台当员工界面、独立 LangSmith 产品 |

**推荐融合方案 D（本 Demo）**

员工主场用独立宽屏三栏工作台（学 A 的气质 + C 的会话结构）：左导航只留「对话 / 评测与案例」+ 最近会话；中栏是 Query / Answer / Citation / 澄清 / 确认 / Tool·Skill 结果；右栏是 **本次 turn 的 Agent 事件流**（学日志与 LangSmith 的「按时间追加」，不学 Workflow 画布那种固定流程图）。

能力只演示已确认链：RAG 知识问答、`create_meeting` Skill（编排 People / Calendar / Meeting 原子 Tool）、周报 Skill、查询信息的最小 READ Tool、以及 timeout→UNKNOWN 与 Confirmation 失效。事件流只渲染真实发生的节点；WRITE 必须出现 Risk/Permission、Confirmation、Result Validation。

不采用 A 的开放 Agent/混合调度、B 的规划、C 的 ReAct。评测页用少量 Fixture 展示 Expected/Actual Route，不追求平台级 5600 条。

## 阶段 R 输入（已由用户确认，供阶段 A 写入 PRD，本阶段不展开产品定义）

- 默认用户：林小北｜产品部；无登录；身份由 Mock UserContext 注入。
- 导航 MVP：仅「对话」「评测与案例」。
- 「查询信息」：一条最小 READ Tool Mock；「执行任务」复用创建会议，不新增执行场景。
- Scene B：`create_meeting` Skill 编排业务规则，底层调原子 Tool，不做纯 Tool。
- Scene D 两条都做（最小可演示）：Tool timeout → UNKNOWN → 状态核验；关键 Slot 修改 → 旧 Confirmation 失效 → 重新确认。
- Trace：事件流，不是固定流程图；不展示恒为 skipped 的节点。
- Python：3.11+。与 `ai_work_companion` 完全独立。
- 原型图只作视觉方向；与文字规格冲突时以规格为准。
